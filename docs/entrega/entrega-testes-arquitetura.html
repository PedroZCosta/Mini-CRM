1. O que foi pedido

Esta entrega complementa a refatoração para Vertical Slice + Clean Architecture já feita no backend: além de organizar o código nesses padrões, o enunciado pede testes unitários de arquitetura que verifiquem, de forma automatizada, que a estrutura do código realmente respeita as regras de dependência — não o comportamento das rotas (isso os testes de domínio e de integração já cobrem), mas quem tem permissão de importar quem.

O enunciado deu uma biblioteca por linguagem, no estilo do ArchUnit original (Java):

LinguagemBiblioteca indicada
JavaArchUnit
C#ArchUnit.NET
NodeArchUnitTS
PythonPyTestArch

O backend do grupo é Node.js (Azure Functions), então a biblioteca usada foi o ArchUnitTS. O nome do pacote publicado no npm é archunit (o projeto se chama ArchUnitTS, mas o pacote é só archunit — detalhe que gerou confusão na primeira busca, registrado no PROMPT.MD). O projeto também fala em "bff e microservices" — este grupo tem um único backend (as Azure Functions), então os testes foram aplicados nele.

A biblioteca é feita para TypeScript, mas também funciona em projetos JavaScript puro — que é o caso daqui (ESM, sem TypeScript). Para isso ela precisa de um tsconfig.json com allowJs: true, usado só para a análise estática (o api/tsconfig.json criado nesta entrega) — nada no runtime da API muda, continua Node puro.

2. Como rodar os testes

Passo a passo para reproduzir qualquer um dos prints pedidos neste documento:

  1. Clonar o repositório e entrar na branch da entrega: 
    git clone https://github.com/PedroZCosta/Mini-CRM.git
cd Mini-CRM
git checkout vertical-slice/clean-architeture
  2. Usar Node.js 22 ou mais novo (node --version) e instalar as dependências da API: 
    npm install --prefix api
  3. Rodar todos os 14 testes de arquitetura de uma vez: 
    node --test --test-reporter=spec api/test/arquitetura.test.mjs
    Saída esperada: 14 linhas começando com ✔ (checkmark verde no terminal) e, no fim, pass 14 / fail 0.
  4. Para rodar só um subconjunto (usado nos prints de cada aluno), acrescenta --test-name-pattern="<trecho do nome do teste>" ao mesmo comando — os comandos exatos estão em cada seção abaixo.

Como tirar cada print: rode o comando indicado num terminal (PowerShell, bash ou o terminal integrado do VS Code), espere a execução terminar, e tire o print da janela do terminal mostrando o comando digitado e a saída completa (os ✔ e o resumo tests/pass/fail no final). Cole o print no espaço indicado logo abaixo do comando correspondente.

3. As 14 regras de arquitetura

Implementadas em api/test/arquitetura.test.mjs (ver no GitHub, commit 292aad9). Resumo de todas, antes do detalhe por aluno:

#RegraO que verifica
1Sem ciclosNenhum arquivo de src/ depende, direta ou indiretamente, de algo que depende dele de volta
2domain × adaptersEntities não dependem de HTTP, Mongo ou massa mock, em nenhuma das 7 slices
3domain × applicationEntities não conhecem Use Cases
4domain × frameworks externosNenhum arquivo de domain/ importa @azure/functions nem mongodb
5application × adaptersDependency Inversion: use case depende do port, nunca da implementação concreta
6–12Isolamento das slicesUm teste por slice — nenhuma das 7 importa arquivo de dentro de outra
13Nome dos portsTodo arquivo em application/ports/ termina em Repository.js
14Nome dos use casesTodo arquivo em application/use-cases/ termina em UseCase.js

As seções 4 a 7 dividem essas 14 regras entre os 4 alunos, na mesma área de responsabilidade de cada um na entrega anterior, com o trecho de código de cada regra e o print pedido.

Slice clientes — regras 2 e 6

Valida que a entidade Cliente não depende de Mongo/HTTP, e que a slice clientes não importa nada de outra slice.

Evidência de código: arquitetura.test.mjs, linhas 36–49 e linhas 97–113

test('domain não depende de adapters em nenhuma slice', async () => {
  const regra = arquivos()
    .inFolder('src/features/*/domain/**')
    .shouldNot()
    .dependOnFiles()
    .inFolder('src/features/*/adapters/**');
  const violacoes = await regra.check();
  assert.equal(violacoes.length, 0, formatar(violacoes));
});

Responsável por instalar o archunit, criar o api/tsconfig.json e validar as regras de abrangência geral (sem ciclos, isolamento de frameworks externos, convenções de nome) — a mesma área de infraestrutura que ele organizou na entrega anterior (shared/).

test('domain não importa @azure/functions nem mongodb diretamente', async () => {
  const regra = arquivos()
    .inFolder('src/features/*/domain/**')
    .should()
    .adhereTo(
      (arquivo) => !/from\s+['"](@azure\/functions|mongodb)['"]/.test(arquivo.content),
      'Entity não pode importar @azure/functions nem mongodb...',
    );
  const violacoes = await regra.check();
  assert.equal(violacoes.length, 0, formatar(violacoes));
});
